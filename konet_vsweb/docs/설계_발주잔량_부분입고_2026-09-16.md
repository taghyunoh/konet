# 설계 — 발주 잔량(미입고) · 부분 입고 · 발주↔매입 양방향 연결 (P1-b, 2026-09-16)

프로그램 목적 ①「재고 파악이 안 돼 중복 발주」·⑥「출고·재고·매입 한 흐름」의 핵심 고리. [기능 강화 분석](konet_기능강화_분석_2026-09-16.md) P1-b.
✅**1단계 구현 완료(같은 날)** — 결정 4건은 전부 추천대로, 단 사용자 확정 「강제는 없다, 메시지 처리」 : 연결된 매입이 있는 발주서 삭제도 **막지 않고** 확인창에 어떤 전표가 끊기는지 적는다. 초과 입고는 확인창 한 번 + 빨강. DDL = docs/sql/20260916_po_remain.sql(이관 포함, 사용자 실행). 손댄 것 = 매퍼 10문(신규 4) · 자바 6(DTO 2·인터페이스 2·서비스·컨트롤러) · JSP 2(poReg·purchaseReg). ⛔재빌드+재기동 뒤 왕복 실측 필요.

## 0. 지금 상태 (코드 실측)

- 발주서 = `TBL_PO_MST/DTL`. 매입전환(`poToPurchase.do`, `UserController.java:1656~`)은 **발주서 전부를 한 장의 매입전표로** 만들고 `TBL_PO_MST.PURCH_SEQ` 에 그 전표 번호만 적는다.
- 매입 쪽(`TBL_PURCHASE_MST/DTL`)에는 발주 번호가 **비고 문자열**(「발주서 20260910-0001 전환」)로만 남는다 — 줄 단위 연결 없음.
- 그래서 「발주했는데 얼마나 들어왔나」를 **셀 수 없다.** 부분 입고는 「전표를 만든 뒤 매입등록에서 수량을 손으로 고치라」가 안내다(`docs/발주서관리_카톡공유.md` 끝줄) — 고치는 순간 발주와의 관계는 사라진다.
- 발주서 화면 「최근발주」 칸(P1-a, 같은 날)은 그래서 「매입전환 됐는지」로만 경고한다.

## 1. 원칙 세 가지

1. **입고수량을 저장하지 않고 센다.** 입고 = 그 발주 줄에 연결된 매입 명세(`ACTION_YN='Y'`)의 수량 합(반품은 음수). 저장해 두면 매입전표를 고치거나 지울 때 어긋난다 — 재고를 원장 합으로만 보는 이 프로그램의 규칙과 같다. **저장하는 것은 연결 키뿐.**
2. **발주 상태도 센다.** 잔량 = 발주수량 − 입고합. 잔량 0 이하 = 완료 · 일부 = 부분입고 · 입고 0 = 미입고. 사람이 저장하는 상태는 하나 — **「더 안 온다」고 닫는 것**(줄 단위 `CLOSE_YN`).
3. **매입전환이 유일한 연결 통로다(1단계).** 발주서 화면 [📦 매입전환]에서 줄마다 「이번 입고」를 넣어 전표를 만든다. 매입등록 화면에서 발주를 골라 가져오는 길은 2단계.

## 2. DB 변경 (DDL 1개 파일)

| 표 | 칸 | 뜻 |
|---|---|---|
| `TBL_PURCHASE_DTL` | **`PO_SEQ` BIGINT NULL · `PO_DTL_SEQ` BIGINT NULL** | 이 매입 줄이 어느 발주서·어느 발주 줄에서 왔는가. 인덱스 `(PO_DTL_SEQ, ACTION_YN)` |
| `TBL_PURCHASE_MST` | `PO_SEQ` BIGINT NULL | 대표 발주서(참고·목록 표시용). 한 전표에 발주 여러 장이 섞이는 것은 2단계 |
| `TBL_PO_DTL` | `CLOSE_YN` CHAR(1) DEFAULT 'N' · `CLOSE_RMK` NVARCHAR(200) | 잔량이 있어도 「더 안 온다」로 닫은 줄 |

- `TBL_PO_MST.PURCH_SEQ` 는 **그대로 둔다**(옛 자료·목록 표시가 쓴다). 새 규칙에서는 「마지막으로 만든 전표」 뜻으로 계속 갱신.
- ⚠형은 가리키는 표를 그대로 베낀다 — `PO_SEQ`·`PO_DTL_SEQ` 둘 다 BIGINT(발주 표가 BIGINT IDENTITY).
- **옛 자료 이관 SQL 1회** : 이미 `PURCH_SEQ` 가 있는 발주서는 그 전표 명세와 발주 명세를 `PROD_CD`(같은 품목 여러 줄이면 `ROW_NO` 차례)로 짝지어 `PO_SEQ/PO_DTL_SEQ` 를 채운다. 못 짝지은 줄은 비워 둔다(= 입고 0 으로 보임 → 사람이 확인).

## 3. 서버

| 항목 | 내용 |
|---|---|
| `poToPurchase.do` 개편 | 줄별 수량을 받는다 — `items=[{poDtlSeq, boxQty, eaQty, qty}]`. 0 인 줄은 전표에서 뺀다. 만든 매입 명세마다 `PO_SEQ/PO_DTL_SEQ` 기록, 전표 머리에도 `PO_SEQ`. 저장 경로는 종전처럼 `savePurchase`(원장·단가 이력 파생 그대로). 종전 「이미 전환 → 409」 규칙은 **「잔량 0 인 줄만 남았다」**로 바꾼다(그래도 force 로 추가 가능 — 초과 입고). |
| 잔량 SQL `selectPoRemain` | 발주 줄마다 `발주 QTY · 입고합(SUM 매입 DTL.QTY, 반품 −) · 잔량 · CLOSE_YN`. 발주서 단위(poSeq)와 품목 단위(prodCd 합 = **입고예정**) 두 꼴. |
| `poDetail.do` · `poList.do` | 줄에 `inQty·remainQty·closeYn`, 머리에 `inCnt/totCnt`·상태(미입고/부분/완료/마감). |
| `poRecentByProd.do`(P1-a) | 경고 기준을 `purchSeq 유무` → **`잔량 > 0`** 으로. 「최근발주」 칸에 `잔량 18` 을 같이 보여 준다. |
| `selectStockQtyMap`/`selectStockMstList` | **입고예정** = 품목별 잔량 합을 LEFT JOIN 으로 얹는다(재고현황·발주서 「미입고」 칸). |
| 매입등록 저장 | `PurchaseDtlDTO` 에 `poSeq/poDtlSeq` 추가, INSERT 칸 추가. 화면이 줄에 실어 나르므로 **전표를 고쳐 저장해도 연결이 안 끊긴다**(savePurchase 는 명세를 지우고 다시 넣는 방식이라 화면이 안 실으면 연결이 날아간다 — 여기가 함정). |
| 발주 줄 마감 `poLineClose.do` | `CLOSE_YN`·사유 저장/해제. |
| 발주서 삭제 | 연결된 매입 명세가 있어도 **막지 않는다** — 확인창에 「매입전표 N장(번호…)이 이 발주를 보고 있습니다. 지워도 전표·재고는 그대로, 입고·잔량 연결만 끊깁니다」 ← 결정 ② (사용자 「강제 아님, 메시지 처리」) |

## 4. 화면

**발주서(poReg.jsp)**
- [📦 매입전환] 창 = 줄 표 `품목 · 발주 · 기입고 · 잔량 · 이번 입고(입력)`. 이번 입고 기본값 = 잔량. 전부 0 이면 「들어온 것이 없습니다」. 매입일자·창고·결제 조건은 종전 그대로.
- 명세 표 「최근발주」 옆에 **「미입고」** 칸(= 그 품목의 다른 발주 잔량 합). P1-a 때 못 넣은 칸.
- 줄마다 `기입고/잔량` 작은 글씨 + 잔량 있는 줄 [마감] 체크(사유). 완료 줄은 흐리게.
- 목록의 「매입전환」 열 → **「입고」** 열 : `✔ 완료` / `부분 12/30` / `미입고` / `마감`.
- 발주서 수정 때 수량을 **이미 입고된 양보다 줄이면** 경고(막지는 않음).

**매입등록(purchaseReg.jsp)**
- 줄에 `poSeq/poDtlSeq` 를 보이지 않게 실어 나른다(emptyRow·저장 payload). 연결된 줄은 코드 옆에 작은 「📋 발주 0910-0001」 표시. 이번엔 여기까지.
- 2단계 : [📋 발주서에서 가져오기] — 잔량 있는 발주 줄을 골라 담기.

**품목별재고현황(logistics_demo2.jsp 패널) · 재고 일괄조정**
- 「입고예정」 열 추가(2단계, SQL 만 되면 한 줄).

## 5. 규칙·엣지

| 경우 | 처리 |
|---|---|
| 매입 반품(TRX_GB 반품) 줄이 발주에 연결 | 입고에서 뺀다 → 잔량이 되살아난다 |
| 발주보다 많이 입고 | 허용, 잔량 음수 = 「초과 입고」 빨강 ← 결정 ③ |
| 발주 없이 등록한 매입 | 연결 없음(지금과 같음) |
| 매입전표 삭제 | 명세가 사라지므로 잔량이 저절로 복원(계산이라 손댈 것 없음) |
| 매입전표 편집 저장 | 화면이 `poDtlSeq` 를 실어 보내면 유지 · 줄을 지우면 그 줄 입고만 빠짐 |
| 같은 품목 두 줄인 발주 | 줄 단위 키라 문제없음(이관 SQL 만 ROW_NO 로 짝) |
| 발주서 삭제, 연결 매입 있음 | 확인창으로 알리고 진행(막지 않음) ← 결정 ② |
| 한 전표에 발주 여러 장 | 2단계(매입등록 가져오기에서) |

## 6. 단계와 품

| | 내용 | 손대는 것 |
|---|---|---|
| **1단계(핵심)** | DDL + 이관 · 전환 창 줄별 입고 · 연결 저장 · 잔량 SQL · 발주서 화면(전환 창·목록 입고 열·미입고 칸·줄 마감) · 매입등록 연결 보존 · 최근발주 경고 기준 | DDL 1 · 매퍼 6~8문 · 자바(컨트롤러·서비스·DTO) · JSP 2 → **재빌드+재기동** |
| ✅**2단계(같은 날 완료)** | 품목별재고현황 「입고예정」 열(`selectStockMstList` LEFT JOIN + `StockMstDTO.poRemainQty`, 총합계 줄·매칭코드 하위행 10열) · 매입등록 **[발주분]** 팝업(`selectPoOpenLines`/`poOpenLines.do` — 잔량 남은 발주 줄, 이번 입고 기본 잔량, 순서대로 담기, 거래처 비면 첫 줄 거래처로, 다른 거래처 줄은 확인창) · 한 전표 여러 발주 = 줄마다 연결이라 저절로 · 매입 머리 대표 발주 `poSeq` | 매퍼 2 · 자바 5 · JSP 2 → 재빌드+재기동 |

검증 = 시뮬(잔량·상태·초과·반품·마감) + 가짜 회사 왕복 : 발주 30 → 12 입고(부분 12/30) → 18 입고(완료) → 전표 삭제 → 잔량 30 복원 → 반품 5 → 잔량 5 → 마감.

## 7. 결정할 것 4

1. **입고를 저장하지 않고 센다** — 추천. (저장하면 빠르지만 전표 수정·삭제 때마다 맞춰 줘야 하고, 한 번 어긋나면 찾기 어렵다.)
2. **연결된 매입이 있는 발주서 삭제** — ~~막기(추천)~~ → **확인창만**(사용자 확정 「강제는 없다」).
3. **초과 입고** — 허용하고 빨강(추천) / 막기.
4. **매입등록 [발주서에서 가져오기]** — 2단계(추천) / 1단계에 포함.
