> 대상 화면 : **매출내역**(정산서 × 출고내역 대사) · **매출마감**(월 매출 확정)
> 관련 쿼리 : `User_SQL.xml` 의 `selectClosing` / `selectClosingUnmatched` / `selectShipoutMst`
> 최종 정리 : 2026-07-25 (수치는 모두 2026-07 실측)

---

## 1. 왜 안분이 필요한가 — 두 자료의 단위가 다르다

| | 테이블 | 단위 | 사업장 정보 |
|---|---|---|---|
| **정산서** (출고장이 준 엑셀) | `TBL_SALES_MST` | **발주 단위** | **없음** |
| **출고내역** (발주현황표) | `TBL_SHIPOUT_MST` | **발주 × 사업장 단위** | `BIZ_CD`, `BIZ_NM` |

정산서에 사업장 칸이 없다는 건 스키마로 확인됩니다.

```sql
SELECT TABLE_NAME, COLUMN_NAME
  FROM INFORMATION_SCHEMA.COLUMNS
 WHERE TABLE_NAME IN ('TBL_SALES_MST','TBL_SHIPOUT_MST')
   AND COLUMN_NAME LIKE '%BIZ%'
 ORDER BY TABLE_NAME;
-- → TBL_SHIPOUT_MST 2행(BIZ_CD, BIZ_NM) / TBL_SALES_MST 0행
```

정산서 전체 컬럼(참고) : `SALES_SEQ, JOB_SEQ, ACTION_YN, ROW_NO, SRC_FILE, UPLOAD_DTTM, DC_CD, DC_NM,
ORD_NO, ORD_ITEM_NO, ITEM_CD, ITEM_NM, SPEC, UNIT, ORD_QTY, SETTLE_QTY, SETTLE_AMT, DLV_DT, OUT_DT,
OUT_QTY, SALE_PRICE, SALE_AMT, DLV_TYPE, TAX_GB, REG_*, UPD_*`

**출고장(DC)까지는 있고 사업장(점포)은 없습니다.** 그래서 매출마감이 사업장별로 집계할 때
정산금액을 나눌 근거가 정산서 안에는 없고, 우리 출고 자료의 수량 비율로 배분(=안분)합니다.

## 2. 대사키

```
대사키 = 납품일자(DLV_DT) + 출고장 + 품목코드(ITEM_CD)
```

출고장은 표기가 두 표에서 달라(`평택` vs `평택물류센터`) **코드로 환원**해서 맞춥니다.
`DC_CD` 가 있으면 그대로, 없으면 이름에서 지역을 찾아 코드로 바꿉니다.

```sql
CASE WHEN ISNULL(t.DC_CD,'') <> '' THEN UPPER(LTRIM(RTRIM(t.DC_CD)))
     WHEN ISNULL(t.DC_NM,'') LIKE '%용인%' THEN 'E100'
     WHEN ISNULL(t.DC_NM,'') LIKE '%왜관%' THEN 'E200'
     WHEN ISNULL(t.DC_NM,'') LIKE '%김해%' THEN 'E300'
     WHEN ISNULL(t.DC_NM,'') LIKE '%광주%' THEN 'E400'
     WHEN ISNULL(t.DC_NM,'') LIKE '%평택%' THEN 'E500'
     WHEN ISNULL(t.DC_NM,'') LIKE '%제주%' THEN 'E600'
     WHEN ISNULL(t.DC_NM,'') LIKE '%오산%' THEN 'E700'
     ELSE '' END
```

날짜는 양쪽 다 `REPLACE(ISNULL(DLV_DT,''),'-','')` 로 8자리 문자열로 맞춥니다.

### 왜 발주번호(ORD_NO+ORD_ITEM_NO)를 키로 쓰지 않나

원리상으로는 발주 단위가 더 정밀합니다. 그런데 실측하면 **매칭률이 오히려 떨어집니다.**

```sql
-- 발주번호 채움 비율 (2026-07)
SELECT COUNT(*) AS 전체행,
       SUM(CASE WHEN ISNULL(ORD_NO,'')<>'' THEN 1 ELSE 0 END) AS 발주번호있음
  FROM TBL_SHIPOUT_MST
 WHERE ACTION_YN='Y'
   AND REPLACE(ISNULL(DLV_DT,''),'-','') BETWEEN '20260701' AND '20260731';
-- → 4,184행 중 3,760행 (424행 = 10% 비어 있음).  정산서는 1,689행 전부 채워져 있음
```

| 대사키 | 매칭되는 정산금액 | 비율 |
|---|---:|---:|
| 발주번호 + 항번 | 113,113,958 | 81.8% |
| **납품일자 + 출고장 + 품목 (현재)** | **121,725,267** | **88.0%** |
| 하이브리드(둘 중 되는 대로) | 121,725,267 | 88.0% |
| 발주번호로**만** 되는 금액 | **0** | — |

발주키로 되는 건은 전부 현재키로도 됩니다. 즉 **발주키를 얹어도 대사되는 금액이 1원도 안 늘어납니다.**

안분 결과가 달라지려면 *같은 키 안에 발주가 2건 이상이고 그 단가가 서로 달라야* 하는데,
2026-07 기준 그런 키는 **0건**입니다(발주 2건 이상인 키는 30건 5,179,258원이나 단가는 모두 동일).

→ **현재키를 유지하고, 단가가 섞이는 순간만 감지**하기로 확정했습니다.
매출내역 요약줄에 `⚠ 키당 단가 혼재 N건` 이 뜨면 그때 발주 단위 안분을 얹으면 됩니다.

## 3. 안분 공식

```
행 매출액 = 그 키의 정산금액 × (그 행의 출고수량 ÷ 그 키의 출고수량 합)
```

`selectClosing` 구현(발췌):

```sql
-- 같은 대사키의 출고수량 합 / 행수 (안분 분모)
SUM(ISNULL(s.CUR_QTY,0)) OVER (PARTITION BY dk.dcKey, s.ITEM_CD, dk.dlvKey) AS keyQty,
COUNT(*)                 OVER (PARTITION BY dk.dcKey, s.ITEM_CD, dk.dlvKey) AS keyRows

-- 매출액
CASE WHEN v.stlAmt IS NULL THEN v.outQty * v.saleUnit          -- 정산서 없음 → 판매단가 추정
     WHEN v.keyQty <> 0
       THEN v.stlAmt * (CAST(v.outQty AS DECIMAL(19,6)) / CAST(v.keyQty AS DECIMAL(19,6)))
     ELSE v.stlAmt / CAST(v.keyRows AS DECIMAL(19,6)) END      -- 분모 0 → 행수 균등 배분
```

**분모가 0인 경우**는 반품이 상쇄돼 그 키의 출고수량 합이 0이 되는 상황입니다(2026-07 실측 8키).
그대로 두면 정산금액이 통째로 0원 처리돼 369,865원이 사라졌습니다 → 행수 균등 배분으로 고쳤습니다.

**출고장별 탭에서는 나눈 값이 다시 합쳐지므로 정산서 금액과 정확히 일치합니다.**
나뉜 건 사업장 축으로 볼 때뿐입니다.

## 5. 근거 배지

`saleSrc`(매출액 근거) / `inSrc`(매입단가 근거) 컬럼으로 내려가며 화면에 `(…)` 로 표시됩니다.

| 배지 | 뜻 | 정확도 |
|---|---|---|
| **정산** | 정산서 금액이 이 줄 하나로 통째로 들어감. 표시 단가는 매출액÷출고수량 역산값 | ★★★ 확정 |
| **정산안분** | 그 키의 출고가 여러 줄로 나뉘어 출고수량 비율로 배분. 분모 0이면 행수 균등 배분 | ★★☆ 확정(배분) |
| **이력** | 정산서 미도착 → 판매단가 이력(`APPLY_DT ≤ 납품일자` 최신, **공통가만**)으로 계산 | ★☆☆ 추정 |
| **마스터** | 정산서·이력 둘 다 없음 → `TBL_PROD_MST.SALE_PRICE`. 마스터에도 없으면 **0원** | ☆☆☆ 추정 |
| **출고미상** | 정산서엔 있는데 출고 자료가 없음. 매출액은 정산서 확정, 수량은 정산서 `OUT_QTY`, **매입액만 추정** | 자료 보완 |

매입단가 배지는 별개 계열입니다 — `이력` / `마스터` / `추정`(출고미상 줄).
**매입에는 `정산`이 없습니다** — 정산서는 우리가 받을 돈이라 원가와 무관합니다.

정산서가 도착하면 `이력`·`마스터` 줄은 자동으로 `정산` 으로 바뀝니다.

## 6. 출고미상 — 정산서에는 있는데 출고 자료가 없는 건

매출마감은 출고 테이블에서 출발하므로 구조적으로 이 건을 못 잡습니다.
그대로 두면 매출마감이 매출내역보다 그만큼 적어져(2026-07 실측 **111건 16,640,146원**)
두 화면을 나란히 설명할 수 없습니다. → `selectClosing` 에 `UNION ALL` 로 편입했습니다.

```sql
-- 출고미상 줄의 구성
outQty    = 정산서 OUT_QTY            -- 출고 자료가 없으니 청구 수량으로 대신
salesAmt  = 정산서 SALE_AMT           -- 확정
costAmt   = 정산서 OUT_QTY × 매입단가  -- 추정 (안 넣으면 전액이 순마진에 얹힘)
bizCd/Nm  = '' / '(사업장 미상)'
saleSrc   = '출고미상' , inSrc = '추정'
```

발주현황표를 올려 출고 자료가 생기면 **이 줄은 사라지고 정상 줄로 흡수**됩니다(자동 해소).

목록 조회는 `selectClosingUnmatched` (화면: 매출마감 요약줄의 `⚠ 출고미상 N건 · M원 포함` 클릭).

원인 분류 쿼리:

```sql
-- '출고자료없음(업로드누락 의심)' / '날짜어긋남(±3일)' / '출고장어긋남' 분류
-- 2026-07 결과 : 아예 없음 4건 10,946,000원(금액의 66%) · 날짜어긋남 32건 · 출고장어긋남 54건
```

## 7. 기간 귀속

```
기간 기준 = 납품일자(DLV_DT).  없으면 출고일자(SHPOUT_DT) 로 폴백
```

정산서에는 출고일자가 아예 없습니다. 마감이 출고일자로 귀속하면 월 경계에서 정산서와 계속 어긋나므로
**2026-07-25 부터 매출마감도 납품일자 기준**으로 바꿨습니다(매출내역과 동일).

단가 기준일도 납품일자입니다 — 먼 지역은 발주분을 하루 당겨 출고해서,
출고일자로 맞추면 `적용일자(발주일) > 출고일자` 가 되어 확정단가가 영영 안 걸립니다.

정산서 전액            138,365,413
+ 미정산 출고 추정      116,485,130

```

```

**주의 — 추정분의 편의(bias)**
이미 정산서가 온 키에서 "추정했더라면" 값을 실제 청구액과 비교하면 **평균 1.9% 높습니다**
(124,018,317 vs 121,725,267). 출고수량이 청구수량보다 1.3% 많고, 우리 판매단가가 조금 높기 때문입니다.
보정계수는 넣지 않습니다 — 월·품목 구성에 따라 흔들리고, 정산서가 도착하면 자동으로 실제값으로 바뀝니다.
**확정 매출은 정산서가 다 온 뒤가 정확합니다.**

## 9. 성능 (2026-07-25 실측)

| 쿼리 | 개선 전 | 개선 후 |
|---|---:|---:|
| `selectClosing` (매출마감·마감현황) | 16,030 ms | **448 ms** |
| `selectClosingUnmatched` (출고미상) | 3,950 ms | **51 ms** |
| `selectShipoutMst` (매출내역 출고) | 1,067 ms | **656 ms** |

테이블은 작습니다(출고 11,213행 / 정산서 5,067행). 느렸던 건 크기가 아니라 **행마다 같은 집계를 다시 실행하는 패턴** 셋이었습니다.

**① 정산서 집계를 임시테이블 `#SLK` 로** (12초 → 0.4초)
인라인 파생테이블이면 옵티마이저가 출고 행마다(4,184회) 집계를 재실행했습니다.
`SET NOCOUNT ON` + `SELECT INTO #SLK` + 클러스터 인덱스 후 조인합니다. UNION 쪽 출고미상도 같은 `#SLK` 를 재사용합니다.
※ 다른 방법은 모두 더 나빴습니다 — CTE 재구성 **27초**, `TOP + ORDER BY` 실체화 **48초**, `OPTION (HASH JOIN)` 은 `OUTER APPLY` 때문에 **계획 생성 불가**.

**② `NOT EXISTS` → 출고 키 집합 LEFT JOIN** (3.7초 → 0.05초)
정산서 행마다 출고 테이블을 다시 뒤졌습니다. 출고장 키가 `CASE` 식이라 인덱스를 못 탑니다.

**③ `firstDttm` 상관 서브쿼리 → 윈도우 함수** (871ms 절감)
"같은 품목 최초 업로드일시"를 행마다 같은 테이블에서 다시 구했습니다.
`MIN(UPLOAD_DTTM) OVER (PARTITION BY SHPOUT_DT, DC_CD, BIZ_CD, ITEM_CD)` 로 한 번에 계산합니다.
파티션 범위가 기간·`ACTION_YN` 과 무관해야 하므로 **필터 이전 단계**(FROM 서브쿼리 안)에서 계산합니다.

### 인덱스

`TBL_SHIPOUT_MST` 에는 PK(SEQ) 하나뿐이었습니다. 2026-07-25 추가:

```sql
CREATE INDEX IX_SHIPOUT_DLV ON TBL_SHIPOUT_MST(ACTION_YN, DLV_DT)
    INCLUDE (ITEM_CD, DC_CD, DC_NM, BIZ_CD, BIZ_NM, VENDOR_CD, VENDOR_NM, CUR_QTY, ITEM_NM, SHPOUT_DT);
CREATE INDEX IX_SHIPOUT_ITEM ON TBL_SHIPOUT_MST(ITEM_CD, DLV_DT);
```

- `IX_SHIPOUT_DLV` — 마감 쪽에서 사용 중(seek 13회)
- `IX_SHIPOUT_ITEM` — **아직 사용 0회.** 계속 0이면 지우는 게 낫습니다(쓰기 비용만 냄)
- 매출내역 출고조회는 `SHPOUT_DT` 로 거르므로 위 인덱스로는 안 빨라집니다 — 그쪽 병목은 ③이었습니다

사용 여부 확인:

```sql
SELECT i.name, s.user_seeks, s.user_scans, s.user_updates
  FROM sys.indexes i
  LEFT JOIN sys.dm_db_index_usage_stats s
         ON s.object_id = i.object_id AND s.index_id = i.index_id AND s.database_id = DB_ID()
 WHERE i.object_id = OBJECT_ID('TBL_SHIPOUT_MST');
```

### 새 쿼리를 짤 때 주의

`SELECT` 목록이나 `WHERE` 안의 **상관 서브쿼리**는 행 수만큼 실행됩니다. 특히 조인/비교에
`CASE`·`ISNULL`·`REPLACE` 같은 식이 끼면 인덱스를 못 타 매번 전체 스캔이 됩니다.
집계는 **한 번 만들어 조인**하고, 행별 최소/최대는 **윈도우 함수**를 쓰세요.
